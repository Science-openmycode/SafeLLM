# 2　应用背景与目标

## 00:15—01:32

【画面：应用场景框架图，从左向右讲解】

这张图的左侧是模型所有者，右侧是提供算力的云端服务器。

模型所有者先在本地可信环境中，对原始模型执行一次离线改造，得到结构保持不变、参数已经转换的混淆模型。随后，混淆模型被部署到现有的云端推理服务器。

在线隐私推理时，用户请求先在本地完成保护处理。云端使用混淆模型执行计算并返回混淆结果，可信侧再恢复真实回答。

我们按照「诚实且好奇」的威胁模型设计系统。云端服务器会按照协议执行计算，同时可能观察收到的模型、请求和中间数据。因此，系统只向云端暴露混淆模型、混淆请求和混淆结果。

我们要解决的问题，是在使用云端 GPU 算力的同时，避免原始模型、用户提示词和真实回答直接暴露给云端。

# 5　总体技术路线

## 03:30—04:23

【画面：总体技术路线图，先指 A，再指 B】

总体技术路线分为两个模块。

A 是离线模型转换模块，只在本地可信环境中执行一次。系统从原始模型 M 出发，建立用户提示词与 TEE、模型中间层与 TEE 之间的安全通道，并对提示词表示和模型参数实施同步变换，得到功能等价的混淆模型 M′。

转换完成后，系统生成云端部署包。云端可以继续使用现有的 PyTorch、Transformers 和 CUDA 环境，也可以使用软件提供的一键部署功能。

B 是云端混淆推理模块，每次请求都会执行。客户端把提示词转换为 Token 并加密，云端混淆模型完成推理后返回加密回答，可信侧再执行解密和解码，得到真实回答。

# 6　TEE 入口与 GPU 模型主体

## 04:23—05:38

【画面：TEE 推理主线图，从客户端指向 TEE Embedding，再指向 GPU】

TEE 是由硬件隔离机制保护的可信执行环境。即使位于云端服务器中，它仍能保护内部代码、明文数据和密钥的机密性与完整性。

客户端先通过 tokenizer 将提示词编码为 Token ID，再通过国密安全通道加密发送给云端 TEE。

TEE 完成认证和解密，得到原始 Token ID。原始 Token 只在 TEE 私有内存中出现，宿主系统和 GPU 都无法直接读取。

TEE 使用原始 Token ID 查询私有 Embedding 矩阵，得到私有坐标下的初始隐藏向量 z0。随后，TEE 把 z0 发送给 GPU 模型主体。

GPU 运行改造后的 Transformer。模型权重、中间隐藏状态和 KV Cache 都处于私有坐标系中。完成全部 Transformer 层计算后，GPU 返回最终私有隐藏向量 zL。

由于 GPU 缺少坐标密钥，它无法从 z0、zL 或中间状态反推出原始 Token 和原始模型表示。

---

# 7　LM Head 安全外包与自循环

## 05:38—06:38

【画面：指向 TEE LM Head、外部 Head、结果返回和自循环箭头】

TEE 接收 zL 后，先恢复最后一个位置的有效隐藏向量 h。LM Head 需要把 h 投影到完整词表空间，这里包含一次规模较大的矩阵乘法。

为了继续利用 GPU 算力，TEE 把这部分计算安全外包。TEE 先对 h 做独立坐标变换，再叠加仅使用一次的随机掩码，得到外部 Head 的输入 u。

外部 GPU 使用变换后的 Head 权重完成矩阵乘法。它只能看到 u、变换权重和被掩码的计算结果，无法获得 h、随机掩码和真实 logits。

结果返回 TEE 后，TEE 去除掩码，并通过 Freivalds 随机校验确认结果没有被篡改。只有通过校验的结果才能进入采样，得到下一个原始 Token ID。

这个 Token 有两个去向：一份经过加密返回客户端，用于恢复回答；另一份留在 TEE 内，再次查询私有 Embedding，并结合 KV Cache 进入下一轮 Decode。模型按这个过程逐个生成 Token，直到遇到结束标记。

# 8　一次推理中的真实数据

## 06:38—08:10

【操作：点击「运行」，按顺序向下查看五个阶段】

本次输入的问题是：「请用一句话说明北京是什么地方。」

客户端先把完整提示词编码为 37 个 Token，再将 Token ID 和生成参数加密。网络中只能观察到密文、随机数和认证标签。

TEE 解密后得到 37 个原始 Token，并查询私有 Embedding。得到的 z0 形状为 `[1, 37, 1152]`，分别表示 1 个请求、37 个 Token，以及每个 Token 对应的 1152 维私有隐藏向量。

GPU 随后运行 24 层 Transformer，输出 zL。zL 的形状仍然是 `[1, 37, 1152]`，具体数值已经经过 24 层模型计算，因此与 z0 不同。

TEE 从 zL 恢复有效隐藏向量 h，维度为 896。随后生成带一次性掩码的 u，并把 LM Head 的大矩阵乘法交给外部 GPU。

外部 Head 返回 151,936 个词表候选结果。TEE 去除掩码，完成两轮 Freivalds 校验，再选出本轮的原始 Token ID 68990，对应回答开头的「北京」。

本轮得到的 Token 一方面加密返回客户端，另一方面进入 TEE Embedding，和 KV Cache 一起开始下一轮生成。

页面中的每个数值都来自当前模型的实际运行，完整回答由多轮相同计算逐 Token 生成。

# 9　安全增强与隐私边界

## 08:10—09:03

【画面：安全增强技术页面】

在单次推理中，提示词和模型都受到完整流程的保护。面对长期、多轮查询，还需要进一步降低频率分析等统计攻击风险。

系统提供两类增强方式。第一类是在客户端加入经过控制的随机噪声，降低多次查询中词元频率与原始提示词之间的相关性。

第二类采用机密级保护策略，定期更新云端混淆模型和相应的私有坐标，使攻击者难以跨版本累计中间表示。

在整个过程中，原始 Token 只会出现在客户端和 TEE 私有内存中。GPU 负责计算量最大的 Transformer 和矩阵乘法，只能接触混淆模型、私有隐藏向量、私有 KV Cache 和被掩码的 Head 数据，无法推导出原始 Token。
