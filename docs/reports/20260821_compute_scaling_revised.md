> TTFT/TPOT之外的扩展指标、单位Token费用、M1成本和SLO门禁通过率见 `20260821_extended_metrics_research.md`。

日期：2026-08-22  
数据版本：v2；正确性断言已移出计时热路径

## 1. 先纠正上一版的口径

`30 Token/s`不是本地CPU的性能，也不是本项目实测得到的固定常数。它只是一个假设的云端模型单会话生成速度，用来把“请求处理能力”换算成“同时生成会话数”。

正确的核算必须分成两段：

```text
本地混淆网关：输入Token + 输出Token → CPU处理时间 → 每核吞吐
云端模型推理：模型结构 + 上下文 + Batch → GPU时间/Token
```

只有在最后估算同时生成会话数时，才需要代入云端模型实际输出速度：

```text
同时生成会话数
= 网关安全请求吞吐 × 每个回答输出Token数 ÷ 模型输出Token/s
```

## 2. 本地混淆：Token与所需有效算力

### 2.1 主换算口径

本节不再用“CPU核”作为基本单位。商业容量规划使用两个量：

```text
业务负载 B = 每秒需要处理的输入Token + 输出Token
有效处理能力 Q = 该设备实际完成的输入Token + 输出Token / 秒
```

所需算力为：

```text
所需设备有效算力份数 = B / Q
```

同一设备、同一业务长度下，私有方案相对普通网关的算力倍率为：

```text
K = 普通网关Token吞吐 / 私有网关Token吞吐

私有方案所需算力 = K × 普通方案所需算力
新增算力比例 = K - 1
```

4个并行Worker的实测换算结果如下。这里的“Token吞吐”同时计入输入和输出Token，不是模型生成速度：

| 平均输入/输出 | 普通网关有效吞吐 | 私有网关有效吞吐 | 同业务量所需算力倍率 | 比普通方案新增算力 |
|---:|---:|---:|---:|---:|
| 128 / 128 | 161.35万 Token/s | 63.38万 Token/s | 2.55倍 | +154.6% |
| 512 / 256 | 235.83万 Token/s | 90.01万 Token/s | 2.62倍 | +162.0% |
| 2,048 / 512 | 428.65万 Token/s | 133.13万 Token/s | 3.22倍 | +222.0% |

最直接的结论：

> 对典型的512输入、256输出请求，若普通网关需要1份有效算力，当前Python私有网关需要2.62份；为维持相同业务吞吐，需要增加约162%的网关计算能力。

例如业务要求处理`1,000万输入+输出Token/s`：

```text
普通网关所需参考算力 = 1,000 / 235.83 = 4.24份
私有网关所需参考算力 = 1,000 / 90.01  = 11.11份
私有方案额外需要       = 6.87份
```

这里的“1份”是当前整机在同一基准程序下的有效处理能力，不等于一个CPU核，也不依赖厂商标称主频或TFLOPS。采购其他机器时，先在候选机器上运行同一基准得到`Q`，再代入`B/Q`即可。

### 2.2 隐私算法本身需要多少操作

对平均输入长度`L_in`、平均输出长度`L_out`和请求率`R`：

```text
每秒词表映射次数 = R × (L_in + L_out)
```

原因是每个输入Token执行一次`tau`，每个输出Token执行一次`inverse_tau`。典型512/256请求每次需要：

```text
512次输入置换 + 256次输出逆置换 = 768次Token映射
```

当前实测中，纯`tau + inverse_tau`平均占`0.540 ms/请求`；完整私有路径相对普通路径新增`1.590 ms/请求`。因此：

| 新增工作 | 时间 | 占私有新增时间 |
|---|---:|---:|
| 词表置换与逆置换本身 | 0.540 ms | 34.0% |
| 本地分词、SSE处理、增量恢复等配套工作 | 1.050 ms | 66.0% |
| 合计 | 1.590 ms | 100.0% |

所以产品扩容不能只计算两次数组查表；完整本地服务还必须计算Tokenizer、流式协议和文本恢复。

### 2.3 实测绝对算力：周期/Token

使用Windows `QueryProcessCycleTime`直接读取进程实际消耗的CPU时钟周期。测试固定单线程、单逻辑处理器亲和性；每个数据点100组、每组20次请求，共2,000次请求。该周期数对应当前i7-12700H和当前Python实现；换处理器架构后应运行同一脚本复标，不能只用标称GHz替代。

| 输入/输出Token | 普通周期/请求 | 私有周期/请求 | 隐私新增周期/请求 | 私有周期/总Token | 隐私新增周期/总Token |
|---:|---:|---:|---:|---:|---:|
| 128 / 128 | 122.36万 | 318.92万 | 196.56万 | 12,458 | 7,678 |
| 512 / 256 | 239.59万 | 637.33万 | 397.73万 | 8,299 | 5,179 |
| 2,048 / 512 | 476.10万 | 1,465.36万 | 989.26万 | 5,724 | 3,864 |

典型512/256请求的绝对计算量为：

```text
普通网关   = 3,120周期/总Token
私有网关   = 8,299周期/总Token
隐私新增   = 5,179周期/总Token
词表映射本身 = 1,902周期/总Token
```

给定业务总Token吞吐`B`，实际算力需求为：

```text
普通算力(Gcycle/s) = B × 3,119.724 ÷ 10^9
私有算力(Gcycle/s) = B × 8,298.511 ÷ 10^9
新增算力(Gcycle/s) = B × 5,178.787 ÷ 10^9
```

具体换算：

| 业务总Token/s | 普通网关 | 私有网关 | 隐私方案新增 | 按最高70%负载应配置的私有有效算力 |
|---:|---:|---:|---:|---:|
| 1万 | 0.031 Gcycle/s | 0.083 Gcycle/s | 0.052 Gcycle/s | 0.119 Gcycle/s |
| 10万 | 0.312 Gcycle/s | 0.830 Gcycle/s | 0.518 Gcycle/s | 1.186 Gcycle/s |
| 100万 | 3.120 Gcycle/s | 8.299 Gcycle/s | 5.179 Gcycle/s | 11.855 Gcycle/s |
| 1,000万 | 31.197 Gcycle/s | 82.985 Gcycle/s | 51.788 Gcycle/s | 118.550 Gcycle/s |
| 1亿 | 311.972 Gcycle/s | 829.851 Gcycle/s | 517.879 Gcycle/s | 1,185.502 Gcycle/s |

这张表就是不以CPU核为单位的算力数量。例如业务峰值为100万总Token/s，完整私有网关实际需要约`8.299 Gcycle/s`；若设备最多使用70%，应采购不低于`11.855 Gcycle/s`的有效网关处理能力。

### 2.4 为什么不换算成TFLOPS/TOPS

本地私有网关的主要工作是Tokenizer、整数索引、JSON/SSE解析、缓存访问和UTF-8文本恢复，不是GPU式浮点矩阵乘法。因此厂商标称TFLOPS/TOPS不能直接换算为网关Token/s。

更底层的跨架构指标应为“退休指令/Token、周期/Token、缓存未命中/Token”。Windows硬件计数器已识别出`InstructionRetired`、`TotalCycles`和LLC计数器，但当前非管理员会话无权采集；在取得管理员硬件计数后，可进一步使用：

```text
Token/s = 有效退休指令/s ÷ 退休指令/Token
Token/s = 有效时钟周期/s ÷ 周期/Token
```

在硬件计数实测完成前，不填写虚构的GIPS或周期/Token数。

### 2.5 当前参考机实测对象

- CPU：Intel Core i7-12700H；
- 操作：Chat Template、Tokenizer、本地 `tau`、SSE JSON解析、`inverse_tau`、增量Detokenize；
- Qwen2.5 Tokenizer和当前产品在线密钥；
- 每个输入/输出组合重复100次；
- 表内时间是单进程串行墙钟服务时间，不含云端模型推理和公网延迟。

从当前20组长度实验中取输入128/512/2,048与输出128/256/512组成9个运营区间点，可用下式解释，拟合优度 `R²=0.9972`：

```text
私有处理时间(ms)
= 0.2982
+ 0.000835 × 输入Token数
+ 0.006727 × 输出Token数
```

与普通明文网关相比，新增计算为：

```text
混淆新增时间(ms)
= 0.2643
+ 0.000842 × 输入Token数
+ 0.003374 × 输出Token数
```

新增计算拟合优度为`R²=0.9983`。

含义：

- 每个请求在该运营区间内有约0.298毫秒拟合固定开销；
- 每增加1,000个输入Token，私有路径增加约0.835毫秒；
- 每增加1,000个输出Token，私有路径增加约6.727毫秒；
- 输出Token更贵，因为每个输出Token都要解析SSE、逆置换并增量恢复文本。

### 2.6 三种请求的时间证据

| 输入/输出Token | 私有处理时间 | 比明文新增 | 一个忙碌CPU核理论请求吞吐 | 每100万请求私有核时 | 每100万请求新增核时 |
|---:|---:|---:|---:|---:|---:|
| 128 / 128 | 1.215 ms | 0.766 ms | 823.2 请求/s | 0.337核时 | 0.213核时 |
| 512 / 256 | 2.491 ms | 1.590 ms | 401.4 请求/s | 0.692核时 | 0.442核时 |
| 2,048 / 512 | 5.425 ms | 3.686 ms | 184.3 请求/s | 1.507核时 | 1.024核时 |

“一个忙碌CPU核理论吞吐”是 `1000 ÷ 单请求毫秒数`。真实服务不能按100%使用CPU，需要预留排队、网络和抖动余量。

最直观的成本结论是：

> 典型512输入、256输出时，每处理100万次完整私有请求共消耗约0.692个CPU核时，其中隐私方案比普通转发多消耗约0.442个CPU核时。

如果CPU核时单价为`P`元、业务量为`N`百万次请求：

```text
完整私有处理CPU成本 = N × 0.692 × P
隐私方案增量CPU成本 = N × 0.442 × P
```

例如CPU核时价格为0.20元，处理1亿次典型请求：

```text
完整私有处理成本 = 100 × 0.692 × 0.20 = 13.84元
相对普通转发新增 = 100 × 0.442 × 0.20 = 8.84元
```

这里只计算本地CPU处理，不包含机器空闲、内存、网络和云端GPU费用。

固定请求为512输入、256输出，每个Worker处理300个请求：

| CPU Worker | 实测私有吞吐 | 相对1核线性效率 | 总Token处理量 |
|---:|---:|---:|---:|
| 1 | 371.6请求/s | 100.0% | 285,414 Token/s |
| 2 | 696.3请求/s | 93.7% | 534,756 Token/s |

### 2.8 如何从有效吞吐换算业务容量

以4个实测Worker为例：

```text
最大实测吞吐 = 1,172.0请求/s
按60%安全利用率 = 703.2请求/s
平均回答长度 = 256输出Token
```

换成日常业务量：

| 4个Worker、60%安全负载 | 可处理请求数 |
|---|---:|
| 每秒 | 703次 |
| 每分钟 | 42,190次 |
| 每小时 | 253万次 |
| 连续24小时 | 6,075万次 |

这组4个Worker实测常驻内存约3.16 GiB，因此落地规格选择4C8G；8GB不是计算公式要求，而是给Python运行时、Tokenizer、密钥、操作系统和流量突发留出空间。

不同云端模型速度对应的持续生成会话数：

| 云端单会话速度 | 4核网关安全承载的持续生成会话 |
|---:|---:|
| 10 Token/s | 18,001 |
| 20 Token/s | 9,001 |
| 30 Token/s | 6,000 |
| 60 Token/s | 3,000 |

因此不能说“4C8G固定支持多少并发”。必须同时给出：输入长度、输出长度、模型Token速度、目标CPU利用率和所用CPU型号。

若业务直接给出请求率，使用更简单的公式：

```text
所需忙碌CPU核
= 每秒请求数 × 单请求处理毫秒 ÷ 1000

规划vCPU
= 所需忙碌CPU核 ÷ 目标利用率
```

## 3. 私有模型是否越大、损耗占比越小

### 3.1 哪部分一定会下降

论文扩维为：

```text
D = d + 2h
```

当前固定 `h=128`，所以 `D=d+256`。Qwen转换没有把Attention内部Head维和FFN中间维一起扩大；它只扩大各投影面对的残差坐标。因此这些投影的结构计算增量接近：

```text
结构增量 ≈ D/d - 1 = 256/d
```

不是 `((D/d)²-1)`。此前使用平方近似描述当前Qwen实现是不准确的。

根据Qwen2.5官方固定revision的真实配置，在512 Token decode上下文下：

| 模型 | d → D | 私有权重字节增加 | 普通投影结构FLOP增加 |
|---|---:|---:|---:|
| 0.5B | 896 → 1,152 | 65.37% | 27.35% |
| 1.5B | 1,536 → 1,792 | 35.43% | 16.20% |
| 3B | 2,048 → 2,304 | 24.80% | 12.20% |
| 7B | 3,584 → 3,840 | 8.25% | 7.04% |
| 14B | 5,120 → 5,376 | 6.14% | 4.91% |
| 32B | 5,120 → 5,376 | 5.51% | 4.95% |
| 72B | 8,192 → 8,448 | 3.70% | 3.10% |

0.5B、1.5B和3B原模型使用词嵌入/LM Head权重绑定，而当前私有checkpoint需要保存两个变换后的权重，因此小模型权重增幅尤其大。7B及以上原模型本来就是非绑定形式，增幅明显下降。

结论：权重占用和普通BF16/FP32投影的百分比损耗，确实总体随隐藏维增大而下降。

### 3.2 哪部分不会自动下降

当前无噪声函数正确的产品checkpoint使用精确度量RMS。每层两个RMS，加最终RMS，每次需要：

```text
z[1,D] × factor[D,d]
```

主计算约为 `2Dd` FLOP，而且当前使用FP64。把它加入完整原始FLOP账本后：

| 模型 | 只算普通结构增量 | 加入精确RMS后的原始FLOP增量 | 精确RMS占私有原始FLOP |
|---|---:|---:|---:|
| 0.5B | 27.35% | 37.15% | 7.15% |
| 1.5B | 16.20% | 26.09% | 7.84% |
| 3B | 12.20% | 23.10% | 8.85% |
| 7B | 7.04% | 17.98% | 9.27% |
| 14B | 4.91% | 23.66% | 15.16% |
| 32B | 4.95% | 15.93% | 9.48% |
| 72B | 3.10% | 18.54% | 13.03% |

这张表已经说明：完整原始FLOP增量不是随模型规模单调下降。14B高于7B，72B高于32B，原因是各型号层数、FFN宽度和精确RMS占比不同。

更重要的是，表中把一个FP64 FLOP和一个BF16 FLOP当成相同单位，只能做算法量计数，不能直接换算运行时间。RTX 3090等消费卡的FP64吞吐远低于BF16/FP32，因此完整运行时损耗可能比原始FLOP百分比更高。

### 3.3 当前能够成立的最终结论

| 问题 | 结论 |
|---|---|
| 模型越大，私有权重增幅是否通常越小？ | 是，当前Qwen2.5系列计算支持。 |
| 模型越大，普通扩维投影的FLOP增幅是否通常越小？ | 是，固定h时近似按256/d下降。 |
| 模型越大，完整私有模型的运行时间损耗是否一定越小？ | 否，当前证据不能支持；精确FP64 RMS使其不单调。 |
| 0.5B完整实测损耗是多少？ | TPOT约+49.61%，TTFT约+47.05%。 |
| 7B、14B、32B、72B完整运行时间是否已实测？ | 没有；当前只有结构公式和隔离核函数证据。 |

所以准确回答是：

> 大模型会稀释扩维权重和普通投影的相对开销，但当前完整私有实现还包含稠密FP64精确RMS，不能据此宣称完整性能损耗一定随参数量下降。

## 4. 要证明完整运行时间趋势需要什么实验

至少选择Qwen2.5-0.5B、1.5B、3B和7B，在同一GPU型号、同一Transformers/PyTorch版本、同一后端上配对测试：

```text
原始模型 / 私有模型
× context = 128 / 512 / 2048
× batch = 1 / 4 / 8
× 每组8轮ABBA/BAAB
× 每轮固定prompt和64输出Token
```

记录TTFT、TPOT、吞吐、显存、功耗和95%置信区间。只有这些完整checkpoint实测结果才能回答“运行时间损耗是否随参数量下降”。当前服务器已经按要求关闭，所以本报告没有伪造这些未运行的数据。
